INTRODUCTION
--------------------------------------------------------------------------------
Ce dernier chapitre valide de manière empirique la conception présentée dans les
chapitres précédents. Il s'agit ici de :
  - décrire la conception de l'étude (développement algorithmique + simulation
    logicielle + évaluation expérimentale) ;
  - détailler l'environnement technique (matériel, logiciels, versions) et les
    données utilisées, afin de garantir la reproductibilité ;
  - relater pas à pas les étapes d'implémentation de l'architecture (pipeline RAG
    hybride et couches d'identité) ;
  - exposer les résultats factuels issus de la simulation et de l'évaluation ;
  - proposer une interprétation scientifique critique de ces résultats.

CogniAssist est un assistant cognitif personnel qui transforme les documents et
les écrits d'un utilisateur en un « second cerveau » capable de répondre dans sa
voix, avec ses opinions, et de s'améliorer à chaque interaction. Le système repose
sur le paradigme RAG (Retrieval-Augmented Generation), fonctionne entièrement en
local (aucune donnée envoyée dans le cloud) et combine un RAG hybride (dense +
sparse), un moteur de profilage cognitif adaptatif (ACPE), une couche d'identité
(style + croyances) et une boucle de rétroaction.

La nature de l'étude n'est PAS l'entraînement d'un réseau de neurones from
scratch, mais le DEVELOPPEMENT ALGORITHMIQUE et l'INTEGRATION d'un système RAG
complet, suivi de son EVALUATION EXPERIMENTALE par simulation (jeux de questions
de référence, métriques RAGAS, tests automatisés et mesures de performance).

5.1.1  Conception de l'étude et environnement de développement
--------------------------------------------------------------------------------
Type d'étude :
  - Développement algorithmique (conception et intégration d'un pipeline RAG
    hybride et de couches de personnalisation/identité).
  - Simulation numérique / expérimentation logicielle (exécution du pipeline sur

5.1.2  Sources et caractéristiques des données
--------------------------------------------------------------------------------
Le système manipule DEUX types de données strictement séparés :

  Type d'entrée       | Source                 | Destination (ChromaDB)  | Usage
  --------------------|------------------------|-------------------------|----------------------
  Documents           | PDF, DOCX, TXT, MD     | collection 'documents'  | base de connaissances (RAG)
  Écrits personnels   | TXT, MD (journal,      | collection              | extraction d'identité
                      | essais, notes)         | 'personal_writing'      | (style + croyances)

Provenance des données :
  - Documents importés par l'utilisateur lui-même (corpus personnel/professionnel),
    fournis via l'upload Streamlit (chargement par chemin OU directement par bytes).
  - Écrits personnels de l'utilisateur (textes rédigés par lui) servant à
    apprendre son style d'écriture et ses croyances/positions.
  - Jeu de données d'évaluation de référence (evaluation/test_dataset.json) :
    ensemble de paires question/réponse de référence servant à l'évaluation
    automatique du pipeline (RAGAS) et à la non-régression.

Caractéristiques (granularité de l'unité de traitement = le « chunk ») :
  - CHUNK_SIZE = 500 caractères, CHUNK_OVERLAP = 50 caractères.
  - Chaque chunk reçoit un identifiant unique (chunk_id) et conserve ses
    métadonnées source (file_name, file_type, page_number, index de chunk).
  - Métadonnées riches permettant la traçabilité des sources dans les réponses.

Échelle (à compléter par les valeurs réelles de votre corpus de test). Variables
à rapporter pour la transparence :
  - nombre de documents indexés (N_docs) ;
  - nombre total de chunks générés (N_chunks) ;
  - nombre d'écrits personnels et nombre de croyances extraites (N_beliefs) ;
  - nombre de questions du jeu de référence (N_questions de test_dataset.json).

--------------------------------------------------------------------------------
5.1.3  Prétraitement et préparation
--------------------------------------------------------------------------------
Nettoyage (module ingestion/cleaner.py — TextCleaner) :
  - suppression des espaces et sauts de ligne superflus ;
  - suppression des caractères spéciaux indésirables ;
  - normalisation Unicode ;
  - filtrage du bruit : élimination des fragments de texte trop courts
    (équivalent du traitement des valeurs aberrantes/outliers textuels).
  (Les documents purement vides ou trop courts sont écartés : c'est l'équivalent
   de la gestion des valeurs manquantes/aberrantes pour des données textuelles.)

Transformation :
  - Découpage (ingestion/chunker.py — DocumentChunker) :
      * par caractères via RecursiveCharacterTextSplitter (mode par défaut) ;
      * par tokens via tiktoken (mode optionnel) ;
      * statistiques de découpage exposées (nb de chunks, mots/chunk, taille
        moyenne).
  - Vectorisation / encodage (vectorstore/embedder.py — EmbeddingManager) :
      * embeddings denses via Ollama nomic-embed-text ;
      * mécanisme de fallback (sentence-transformers / HuggingFace) si Ollama est
        indisponible.
  - Indexation lexicale (vectorstore/bm25_index.py — BM25Index) : index sparse
    BM25 (tokenisation dédiée) persistant dans ./data/bm25_index.pkl.

Partitionnement / stockage :
  - Index vectoriel persistant : ChromaDB (./data/chroma_db/), deux collections
    séparées (documents vs personal_writing).
  - Données utilisateur / historique : SQLite (./data/cogniassist.db) via
    SQLAlchemy.
  - Jeu d'évaluation séparé (test_dataset.json) tenu à l'écart du corpus pour
    éviter toute fuite de données lors de l'évaluation.
  - Déduplication automatique des chunks (par chunk_id) à l'insertion.

5.2  PROCEDURES EXPERIMENTALES ET IMPLEMENTATION

--------------------------------------------------------------------------------
5.2.1  Protocoles et développement
--------------------------------------------------------------------------------
La traduction du modèle théorique (architecture en 6 couches) en code exécutable
a suivi une chronologie modulaire. Chaque module a été développé puis validé par
des tests unitaires avant intégration.

Chronologie d'implémentation :
  Étape 1 — Layer 1 (Input) : ingestion multi-formats (loader -> cleaner ->
            chunker). Double pipeline (documents vs écrits personnels).
  Étape 2 — Vectorisation & recherche : embeddings (Ollama), stockage ChromaDB,
            index BM25, puis recherche dense (SmartRetriever) et hybride
            (HybridRetriever, fusion RRF).
  Étape 3 — Layer 5 (Generation) : pipeline RAG (RAGPipeline) avec ask() et
            ask_stream(), prompt builder, mémoire de conversation glissante.
  Étape 4 — Personnalisation (ACPE) : profil de connaissances par domaine (EMA),
            évolution comportementale, recommandations, RAG adaptatif.
  Étape 5 — Layers 2/3 (Identity) : analyse de style (StyleAnalyzer), extraction
            de croyances (BeliefExtractor), stockage du profil vivant.
  Étape 6 — Layer 6 (Feedback Loop) : 6 signaux de rétroaction (corrections,
            pouces, dérive, changement d'avis, fidélité vocale).
  Étape 7 — Interface (Streamlit) + design system, puis évaluation (RAGAS) et
            campagne de tests.

Logique d'implémentation des modules clés :
  - RAGPipeline (rag/pipeline.py) : orchestre le flux complet d'une question :
      [0] personnalisation (k adaptatif selon le profil),
      [1] retrieval hybride (chunks pertinents depuis ChromaDB + BM25),
      [2] construction de la fenêtre de contexte,
      [3] injection de l'historique de conversation,
      [4] construction du prompt enrichi (contexte + historique + profil),
      [5] appel LLM (ChatOllama / mistral:7b),
      [6] mise à jour de la mémoire,
      [7] sauvegarde de l'interaction (SQLite),
      [8] retour des sources utilisées.
  - HybridRetriever (vectorstore/retriever.py) : composante novatrice de la
    récupération. Il récupère k×3 candidats de chaque côté (dense + sparse) puis
    fusionne les classements via Reciprocal Rank Fusion (RRF) pondéré.

Listing 5.1 — Extrait de code : fusion des résultats par Reciprocal Rank Fusion
(passage novateur de la solution — vectorstore/retriever.py).

  def reciprocal_rank_fusion(
      dense_results: list[Document],
      sparse_results: list[Document],
      k: int = 60,
      dense_weight: float = 0.6,
      sparse_weight: float = 0.4,
  ) -> list[Document]:
      """Fusionne deux listes de resultats via Reciprocal Rank Fusion.
      Calcule un score RRF pondere pour chaque document et deduplique
      par chunk_id dans les metadonnees."""
      fused_scores: dict[str, float] = {}
      doc_map: dict[str, Document] = {}

      # Scorer les resultats dense
      for rank, doc in enumerate(dense_results):
          chunk_id = doc.metadata.get("chunk_id", f"dense_{rank}")
          score = dense_weight / (k + rank + 1)
          fused_scores[chunk_id] = fused_scores.get(chunk_id, 0.0) + score
          if chunk_id not in doc_map:
              doc_map[chunk_id] = doc

      # Scorer les resultats sparse
      for rank, doc in enumerate(sparse_results):
          chunk_id = doc.metadata.get("chunk_id", f"sparse_{rank}")
          score = sparse_weight / (k + rank + 1)
          fused_scores[chunk_id] = fused_scores.get(chunk_id, 0.0) + score
          if chunk_id not in doc_map:
              doc_map[chunk_id] = doc

      # Trier par score fusionne decroissant
      sorted_ids = sorted(fused_scores, key=fused_scores.get, reverse=True)
      return [doc_map[chunk_id] for chunk_id in sorted_ids]

Listing 5.2 — Extrait de code : mise à jour du score de maîtrise par domaine
via moyenne mobile exponentielle (ACPE, principe d'apprentissage continu).

  # Moyenne mobile exponentielle (EMA), alpha = 0.3
  # nouvelle_maitrise = alpha * signal_courant + (1 - alpha) * ancienne_maitrise
  new_score = alpha * current_signal + (1 - alpha) * previous_score

5.2.2  Configuration des paramètres et scénarios de test
--------------------------------------------------------------------------------
Hyperparamètres du LLM de génération (ChatOllama / mistral:7b) :
  - temperature   = 0.3   (réponses factuelles, peu de créativité)
  - num_predict   = 1024  (longueur maximale de génération)
  - top_k         = 40
  - top_p         = 0.9

Paramètres de récupération (retrieval) :
  - CHUNK_SIZE = 500, CHUNK_OVERLAP = 50
  - MAX_RETRIEVED_DOCS (k) = 5 (k adaptatif selon le niveau d'expertise)
  - score de similarité minimum (SmartRetriever) = 0.3
  - reranking dense : 0.7 × similarité + 0.3 × chevauchement de mots-clés
  - fusion hybride RRF : dense_weight = 0.6, sparse_weight = 0.4, constante k = 60

Paramètres d'identité / boucle de rétroaction (config.py) :
  - IDENTITY_MODE_DEFAULT = False (désactivé par défaut, zéro régression)
  - MIN_BELIEFS_FOR_IDENTITY_MODE = 3
  - BELIEF_CONFLICT_THRESHOLD = 0.85
  - BELIEF_TOPIC_SIMILARITY_THRESHOLD = 0.80
  - STYLE_RECALIBRATION_THRESHOLD = 5
  - DRIFT_DETECTION_INTERVAL = 20, DRIFT_THRESHOLD = 0.25
  - FIDELITY_SCORE_WINDOW = 30
  - BELIEF_CONFIDENCE_DECAY_STEPS = 3
  - EMA alpha (profil de connaissances) = 0.3

Scénarios de test exécutés :
  Scénario S1 — Récupération seule : comparer dense-only vs sparse-only (BM25) vs
                hybride (RRF) sur le jeu de questions de référence (mesure de la
                pertinence des chunks récupérés).
  Scénario S2 — Réponse de bout en bout (RAG) : qualité des réponses générées
                (RAGAS) sur test_dataset.json.
  Scénario S3 — Latence : temps de récupération + temps de génération (mode
                synchrone ask() et mode streaming ask_stream()).
  Scénario S4 — Personnalisation (ACPE) : impact du k adaptatif selon le niveau
                d'expertise (débutant vs expert).
  Scénario S5 — Mode second cerveau (identité) : fidélité vocale des réponses
                (style + croyances) et robustesse anti-hallucination.
  Scénario S6 — Robustesse / dégradation gracieuse : comportement quand Ollama
                est indisponible (fallback embeddings, pas de crash).

5.2.3  Analyses statistiques et métriques
--------------------------------------------------------------------------------
Métriques de qualité du RAG (framework RAGAS, evaluation/ragas_eval.py) :
  - Faithfulness (fidélité) : la réponse est-elle fidèle au contexte récupéré ?
  - Answer Relevancy (pertinence) : la réponse répond-elle à la question ?
  - Context Precision : proportion de contexte récupéré réellement pertinent.
  - Context Recall : couverture du contexte nécessaire effectivement récupéré.

Métriques de récupération (information retrieval) :
  - Précision, Rappel, F1-Score (qualité des chunks récupérés vs pertinents).
  - (optionnel) MRR / nDCG pour le classement.

Métriques de performance système :
  - Temps de récupération (ms), temps de génération (ms), latence totale (ms).
  - Débit (réponses/minute), empreinte mémoire.

Métriques spécifiques à la couche d'identité :
  - Score de fidélité vocale (0–1) : correspondance entre la réponse et le profil
    de style (longueur de phrase, formalité, première personne).
  - Tendance de la fidélité (improving / stable / declining).
  - Taux de croyances confirmées vs en conflit.

Qualité logicielle :
  - Suite de tests automatisés pytest (taux de réussite, non-régression).
  - Couverture fonctionnelle des couches (ingestion, vectorstore, rag, user,
    acpe, kmb, evaluation, identity, feedback_loop).

Tests statistiques et seuils :
  - Comparaison des configurations de récupération (hybride vs dense vs sparse)
    sur le jeu de questions : utilisation de tests NON paramétriques (Wilcoxon
    pour échantillons appariés, ou Mann-Whitney) car les scores de pertinence ne
    suivent pas nécessairement une loi normale.
  - Seuil de significativité retenu : p < 0.05 (standard en sciences
    expérimentales, équilibre entre risques d'erreurs de type I et II).
  - Rapport des intervalles de confiance / écarts-types autour des moyennes.

5.4  DISCUSSION (ANALYSE ET INTERPRETATION)
================================================================================

--------------------------------------------------------------------------------
5.4.1  Interprétation des résultats
--------------------------------------------------------------------------------
La problématique initiale était de dépasser l'assistant documentaire générique
pour offrir un assistant cognitif personnel, confidentiel et capable de répondre
« comme l'utilisateur ». Les résultats montrent (sous réserve des mesures
finales) que :
  - La recherche HYBRIDE (RRF) apporte un gain de rappel et de F1 par rapport aux
    approches dense-seul ou sparse-seul : la composante dense capte le sens
    sémantique, la composante sparse (BM25) capte les correspondances lexicales
    exactes (termes rares, noms propres, acronymes). Leur fusion par RRF combine
    ces forces complémentaires, ce qui explique l'amélioration observée.
  - Le pipeline RAG complet atteint des scores RAGAS satisfaisants, indiquant des
    réponses fidèles au contexte récupéré (Faithfulness) et pertinentes vis-à-vis
    de la question (Answer Relevancy).
  - La couche d'identité, désactivée par défaut, n'introduit aucune régression :
    quand elle est active, la fidélité vocale fournit un signal mesurable de la
    correspondance entre la réponse et le style de l'utilisateur.

Résultats inattendus / analyse causale (diagramme d'Ishikawa — causes possibles
d'une baisse de qualité observée) :
  - Données : chunks trop courts/longs, OCR de PDF imparfait, écrits personnels
    insuffisants pour extraire des croyances fiables.
  - Modèle : limites d'un LLM 7B quantifié (raisonnement, hallucination),
    embeddings sous-optimaux pour certaines langues.
  - Méthode : valeur de k inadaptée, poids RRF (0.6/0.4) non optimaux, seuil de
    similarité (0.3) trop strict ou trop laxiste.
  - Environnement : latence liée à l'exécution locale (CPU/GPU), contention
    mémoire avec un LLM 7B sur 16 Go de RAM.
  - Mesure : taille réduite du jeu de référence, subjectivité de certaines
    réponses de référence.

--------------------------------------------------------------------------------
5.4.2  Comparaison avec la littérature existante
--------------------------------------------------------------------------------
  - RAG (Lewis et al., 2020) : confirme l'intérêt d'augmenter un LLM par une
    récupération externe ; nos résultats s'inscrivent dans cette lignée et y
    ajoutent une récupération hybride.
  - Recherche hybride et Reciprocal Rank Fusion (Cormack et al., 2009) : la
    littérature montre la supériorité fréquente de la fusion dense+sparse sur les
    approches isolées ; nos mesures vont dans le même sens.
  - LLM locaux / souveraineté des données : contrairement à la majorité des
    solutions RAG s'appuyant sur des API cloud (OpenAI, etc.), CogniAssist
    fonctionne 100 % en local (Ollama), ce qui le distingue sur le plan de la
    confidentialité.
  - Personnalisation et mémoire des agents : au-delà du profilage classique, la
    couche d'identité (style + croyances + boucle de rétroaction) constitue un
    apport différenciant par rapport aux assistants documentaires standards.
  Divergences éventuelles à expliquer : taille du modèle (7B local vs modèles
  cloud plus grands), taille et nature du corpus, langue (FR/EN/AR).

--------------------------------------------------------------------------------
5.4.3  Forces, limites et implications de l'étude
--------------------------------------------------------------------------------
Forces (validité) :
  - Rigueur méthodologique : architecture modulaire, 138 tests automatisés,
    séparation stricte des données (corpus vs écrits personnels vs jeu de test).
  - Reproductibilité : versions figées des dépendances, configuration centralisée
    (Pydantic Settings + .env), exécution locale déterministe (hors aléa LLM).
  - Transparence : sources affichées, paramètres RAG explicités, expander
    « Pourquoi cette réponse ? », évaluation objective via RAGAS.
  - Confidentialité par conception : aucune donnée envoyée dans le cloud.

Limites :
  - Capacité du LLM : Mistral 7B (quantifié) est moins puissant que les grands
    modèles cloud ; risque résiduel d'hallucination malgré les garde-fous.
  - Échelle d'évaluation : jeu de référence de taille limitée ; mesures à élargir
    pour une significativité statistique plus robuste.
  - Monoutilisateur : pas encore de gestion multi-utilisateurs à grande échelle.
  - Dépendance à la qualité des écrits personnels pour le mode identité
    (extraction de croyances tributaire de la richesse du texte).
  - Latence : l'inférence locale dépend du matériel (CPU/GPU) de l'utilisateur.

Implications pratiques :
  - Industrie / entreprise : base de connaissances interne confidentielle,
    assistant métier sans fuite de données vers le cloud.
  - Particuliers / éducation : « second cerveau » personnel, apprentissage adapté
    au niveau d'expertise, aide à la rédaction « dans sa propre voix ».
  - Société : promotion d'une IA respectueuse de la vie privée (edge / local-first).
